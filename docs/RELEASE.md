# Release checklist

Releases are made from a clean, reviewed commit. Version `0.1.0` is the initial release candidate; the encrypted **file format** is version 1 and is independent of the application version. Changing Cargo's application version does not change the file format.

## Before the first public release

1. Review all files with `git status` and `git ls-files`; make sure no real configurations, credentials, or manual test data are tracked. The `manual-tests/` directory is deliberately ignored.
2. Check that `Cargo.lock` is committed. Do not include `target/` in Git.
3. Run these checks (on both Windows and Linux if possible):

   ```sh
   cargo fmt --all -- --check
   cargo clippy --all-targets --locked -- -D warnings
   cargo test --release --all-targets --locked
   cargo build --release --locked
   ```

4. Confirm the GitHub Actions checks pass on `main` (Windows and Linux).
5. Inspect `cfgtool --version` and `cfgtool --help`, and manually check a plaintext read/write and an encrypted read/write.
6. Tag the **exact tested commit** `v0.1.0`. Make a GitHub Release from that tag; upload the intended Windows/Linux binaries as release assets. Builds on different OS/toolchains may have different hashes even when using the same `Cargo.lock`.

Do not publish development configurations or cryptographic passwords as assets. The source ZIP generated automatically by GitHub is **not** a compiled executable.

## Verify your own compiled binaries

On Windows (PowerShell):

```powershell
Get-FileHash .\target\release\cfgtool.exe -Algorithm SHA256
```

On Linux:

```sh
sha256sum target/release/cfgtool
```

Record each release asset's SHA-256 digest in the GitHub Release notes or a checksum manifest. SHA-256 is useful for detecting corruption and matching a **previously trusted** expected hash. A checksum distributed from the same untrusted location as a replaced binary does **not** authenticate who built the binary.

## How to authenticate a binary

- For an application bundling a **specific version**, embed (pin) the expected SHA-256 digest of that *exact* binary in the consuming application or in another trusted, signed manifest; verify **before** executing it. Every new binary requires a deliberate hash update. The application must obtain its expected hash from a trusted source, not from the downloaded binary's directory.
- For updateable binary releases, use a **digital signature or signed provenance** with a trusted signing identity/key, and verify that identity and the artifact digest before execution. A version string, filename, or `--version` response is not an authenticity check.
- GitHub provides **artifact attestations** and release asset verification for builds/releases configured to produce them. They are not automatically generated by this repository's basic CI workflow. See https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations and https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity .
- Windows Authenticode is an additional option when distributing to Windows users. It requires a suitable signing certificate and release process; verify both signature validity and the expected publisher identity. This repository does not currently sign executables.


## Compatibility

Maintain tests for the v1 encrypted envelope when changing code. Existing v1 files should remain readable in future versions. If an incompatible format is ever necessary, give it a new on-disk format version and provide a migration path rather than silently changing how `version: 1` is interpreted.
